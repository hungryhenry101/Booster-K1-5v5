# 多机协作优化方案详解

## 背景与目标

根据各赛队反映的集中性问题：
1. **机器人定位缓慢**
2. **上场位置集中**
3. **赛间前锋相互抢球**

本优化方案旨在解决上述问题，通过以下三个核心修改实现：

---

## 一、优化上场位置和赛间前锋配合

### 1. 修改 `brain.cpp` - 多机协作核心逻辑

**文件位置**: `src/brain/src/brain.cpp` (约第 486-555 行)

#### 优化目标
- 降低"双抢球冲突"概率（两台机器同时冲球导致互相干扰）
- 让"最有机会先触球的机器人"优先控球，其它机器人转辅助

#### 核心数据结构

```cpp
// 三个核心变量
double tmMinCost = 1e5;    // 所有在线队友中"接近并控制球"的最小代价
int myCostRank = 0;        // 我的成本排名（0=最优，1=有 1 个队友比我优，2+=应让位）
int myStrikerIDRank = 0;   // 我在 striker 中的 ID 排名，用于站位分配
```

#### 计算逻辑

```cpp
// 遍历在线队友，统计三类信息
for (int i = 0; i < aliveTmIdxs.size(); i++) {
    int tmIdx = aliveTmIdxs[i];
    auto tmStatus = data->tmStatus[tmIdx];

    // 1) 记录最小 cost
    if (tmStatus.cost < tmMinCost) tmMinCost = tmStatus.cost;

    // 2) 统计我的 cost 排名
    if (tmStatus.cost < data->tmMyCost) myCostRank++;

    // 3) 统计我在 striker 中的 ID 排名
    if (tmIdx < selfIdx && tmStatus.role == "striker") myStrikerIDRank++;
}

// 写回共享状态
data->tmMyCostRank = myCostRank;
data->myStrikerIDRank = myStrikerIDRank;
```

#### Lead 判定逻辑（双条件退让机制）

```cpp
double BALL_CONTROL_COST_THRESHOLD = 3.0;

// lead 退让条件（满足任一即退出）：
// A. 场上存在"明显更优"的控球队友 (tmMinCost 足够小，且我不是最小)
// B. 我的成本排名 >=2（至少两名队友更适合抢球）
if (
    (tmMinCost < BALL_CONTROL_COST_THRESHOLD && data->tmMyCost > tmMinCost)
    || myCostRank >= 2
) {
    data->tmImLead = false;  // 退出 lead，转为辅助
} else {
    data->tmImLead = true;   // 保持/成为 lead
}
```

#### 效果
- **单机优势**：最优者直接 lead，无需等待
- **双机场景**：次优者自动退让，避免双抢
- **多机场景**：cost 排名>=2 的机器人主动转辅助

### 2. 修改 `brain_tree.cpp` - Assist 助攻站位函数

**文件位置**: `src/brain/src/brain_tree.cpp` (约第 645-750 行)

#### 优化目标
- rank≤1 的辅助机器人在"人数够 + 球在前场"时前插接应，不再固定永远球后 2m
- rank==2/3 分层站位更清晰：一台中场二次接应，一台后场兜底
- 增加 rank==0 和 rank≥4 兜底，防止异常排序时目标点未定义
- 增加场地边界裁剪，防止站位冲出边线

#### 核心实现

##### (1) 几何拦截线计算

```cpp
// 计算"我方球门 -> 球"的拦截线在给定 x 下对应的 y
auto calcBlockLineY = [&](double targetX) {
    const double denom = ballPos.x - ownGoalX;
    if (fabs(denom) < 1e-6) return 0.0;  // 避免除以 0
    return ballPos.y * (targetX - ownGoalX) / denom;
};
```

##### (2) 动态前插判断

```cpp
const int rank = brain->data->tmMyCostRank;
const bool aggressiveAssist = brain->data->liveCount >= 3;  // 人数≥3 时激进

if (rank <= 1) {
    bool ballInAttackHalf = ballPos.x > -fd.circleRadius * 0.5;

    if (aggressiveAssist && ballInAttackHalf) {
        // 进攻站位：球前 1m + 反侧偏移 1.2m（二过一接应）
        targetPose.x = ballPos.x + 1.0;
        targetPose.y = ballPos.y + (ballPos.y >= 0.0 ? -1.2 : 1.2);
    } else {
        // 保守站位：球后 2m 拦截线
        targetPose.x = ballPos.x - 2.0;
        targetPose.y = calcBlockLineY(targetPose.x);
    }
}
```

##### (3) 分层站位表

| Rank | 职责 | X 坐标 | Y 坐标 |
|------|------|--------|--------|
| 0-1 (进攻) | 第一接应 | ball.x + 1.0 | ball.y ± 1.2 |
| 0-1 (保守) | 第一接应 | ball.x - 2.0 | calcBlockLineY |
| 2 | 二次接应 | ball.x - 0.8/1.2 | ball.y * 0.6 |
| 3 | 防守兜底 | ownGoalX + goalAreaLength | calcBlockLineY |
| ≥4 | 异常兜底 | ownGoalX + goalAreaLength | calcBlockLineY |

##### (4) 场地边界约束

```cpp
// X 方向：不压对方禁区太深，不贴我方底线
targetPose.x = cap(targetPose.x,
    oppGoalX - fd.penaltyAreaLength - 0.2,
    ownGoalX + distToGoalline);

// Y 方向：保持边线安全余量
targetPose.y = cap(targetPose.y,
    fd.width / 2.0 - 0.7,
    -fd.width / 2.0 + 0.7);
```

### 3. 修改 `brain_tree.cpp` - GoToReadyPosition 准备站位

**文件位置**: `src/brain/src/brain_tree.cpp` (约第 3126-3213 行)

#### 优化目标
- striker 按 myStrikerIDRank 分配固定槽位（0/1/2/3）
- 对 rank 异常增加兜底，不退化到默认中心点 (0,0)
- 增加 isCrowded 检查：目标点拥挤时自动错位
- 仅对 striker 做错位，goal_keeper 继续固定门前

#### 基础站位分配

```cpp
if (role == "striker") {
    const int rank = brain->data->myStrikerIDRank;

    if (rank == 0) {      // 主 striker：中路偏前
        tx = isKickoff ? -fd.circleRadius : -fd.circleRadius * 2;
        ty = 0.0;
    }
    else if (rank == 1) { // 次 striker：同深度 y 轴拉开
        tx = isKickoff ? -fd.circleRadius : -fd.circleRadius * 2;
        ty = -1.5;
    }
    else if (rank == 2) { // 第三 striker：中后场接应
        tx = -fd.length / 2.0 + fd.penaltyAreaLength;
        ty = fd.circleRadius / 2.0;
    }
    else if (rank == 3) { // 第四 striker：纵向镜像
        tx = -fd.length / 2.0 + fd.penaltyDist;
        ty = -fd.circleRadius / 2.0;
    }
    else {                // 兜底：按 playerId 奇偶分左右
        tx = -fd.length / 2.0 + fd.penaltyDist;
        ty = (brain->config->playerId % 2 == 0 ? 1.0 : -1.0) * fd.circleRadius / 2.0;
    }
}
```

#### 防挤占错位机制

```cpp
// 拥挤检测函数
auto isCrowded = [&](double x, double y, double radius) {
    for (int i = 0; i < HL_MAX_NUM_PLAYERS; i++) {
        if (i + 1 == brain->config->playerId) continue;  // 跳过自己
        const auto &tm = brain->data->tmStatus[i];
        if (!tm.isAlive) continue;  // 跳过离线
        if (norm(tm.robotPoseToField.x - x, tm.robotPoseToField.y - y) < radius) {
            return true;  // 有队友在半径内
        }
    }
    return false;
};

// 仅对 striker 启用错位
if (role == "striker" && isCrowded(tx, ty, 0.8)) {
    const vector<double> yOffsets = {0.0, 0.8, -0.8, 1.6, -1.6};
    double baseY = ty;

    for (double dy : yOffsets) {
        double candY = cap(baseY + dy, fd.width / 2.0 - 0.6, -fd.width / 2.0 + 0.6);
        if (!isCrowded(tx, candY, 0.8)) {
            ty = candY;  // 采用第一个空位
            break;
        }
    }
}
```

## 二、机器人定位参数优化

### 修改 `config.yaml`

**文件位置**: `src/brain/config/config.yaml`

```yaml
locator:
  min_marker_count: 3      # 最少看到几个 marker 才可进行粒子滤波定位
  max_residual: 0.45       # 定位结果容差（原 0.5 -> 0.45 精度提升）
```

#### 参数说明

| 参数 | 原值 | 建议值 | 说明 |
|------|------|--------|------|
| `min_marker_count` | 3 | 3 | 越大越难定位成功，但定位更可靠 |
| `max_residual` | 0.5 | 0.45 | 越大越容易定位，但精度降低；调低可提高定位精度 |

#### 调优建议

- **定位缓慢问题**：可适当降低 `min_marker_count` 到 2，或提高 `max_residual` 到 0.5
- **定位精度问题**：保持 `min_marker_count=3`，降低 `max_residual` 到 0.4 或更低
- **场地光照差**：可提高 `max_residual` 容忍更多误差

## 三、整体协作流程

```
比赛开始
    │
    ▼
┌─────────────────────────────┐
│ 1. 计算多机协作核心量         │
│    - tmMinCost (最小成本)    │
│    - myCostRank (成本排名)   │
│    - myStrikerIDRank (ID 排名)│
└─────────────────────────────┘
    │
    ▼
┌─────────────────────────────┐
│ 2. Lead 判定                 │
│    - 满足退让条件？→ Assist  │
│    - 否则 → Lead (主控球)    │
└─────────────────────────────┘
    │
    ├─────────────┬─────────────┐
    ▼             ▼             ▼
┌───────┐   ┌──────────┐  ┌──────────┐
│ Lead  │   │ Assist   │  │ Ready    │
│ 抢球  │   │ 助攻站位 │  │ 准备站位 │
└───────┘   └──────────┘  └──────────┘
                │                │
                ▼                ▼
        按 rank 分层站位    按 ID 分槽位
        - rank0/1 前插      - 防挤占错位
        - rank2 中场        - 边界裁剪
        - rank3 兜底
```

## 四、预期效果

| 问题 | 优化手段 | 预期改善 |
|------|----------|----------|
| 双抢球冲突 | cost 排名 + lead 退让机制 | 减少 70%+ 碰撞干扰 |
| 上场位置集中 | ID 排名分槽位 + 防挤占 | 自动分散到不同区域 |
| 前锋配合混乱 | rank 分层站位 | 一前二后层次清晰 |

## 五、使用建议

1. **必须修改项**：
   - `config.yaml` 中的 `player_id` 和 `player_role`
   - `game_control_ip` 裁判机 IP

2. **可选调整项**：
   - `ball_control_cost_threshold`：默认 3.0，越大越容易让位
   - `aggressiveAssist` 人数阈值：默认 3，可改为 4 更保守
   - `yOffsets` 错位偏移量：默认{0, ±0.8, ±1.6}，可根据场地调整

3. **调试建议**：
   - 开启 `log_ball_pos: true` 记录球位置
   - 观察 `tmMyCostRank` 和 `myStrikerIDRank` 日志
   - 使用 rerun Viewer 实时可视化站位

---

## 六、注意事项

1. **通信依赖**：本方案依赖队友间通信 (`enable_com: true`)，通信故障时兜底逻辑生效
2. **角色一致性**：所有队友的 `player_id` 必须唯一且连续
3. **测试验证**：建议先在训练模式验证，确认各 rank 行为符合预期后再参赛
